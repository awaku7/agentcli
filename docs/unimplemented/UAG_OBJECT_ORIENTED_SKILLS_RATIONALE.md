# 手順書型 Skill から状態付きオブジェクトへ
## UAG におけるオブジェクト指向 Skill 拡張の設計根拠

- 文書状態: 完成（2026-11-27）
- 対象: UAG / `awaku7/agentcli`
- 対応する設計書: `docs/unimplemented/UAG_OBJECT_ORIENTED_SKILLS_DESIGN.md`（本書は「どう作るか」ではなく「なぜこの形か」を記録する）

## 要旨

Agent Skills の標準形式は手順書型であり、配布と可搬性に優れる一方、実行の単位としては、状態の置き場所が会話しかない、呼び出しに型がない、並行する文脈で状態の分離が保証されない、という限界がある。本書は、UAG におけるオブジェクト指向 Skill 拡張について、配布形式を標準のままに保ち、明示的に選んだ Skill だけを実行時のオブジェクト（定義とインスタンス、型付きメソッド、私有状態）として扱うという設計の根拠を記録する。あわせて、互換性契約を実装に先立って固定する理由、制限付きで採用した継承・インターフェース・オーバーライドの規則、残る未解決の論点（呼び出し口、既存の文脈保存との重なり、状態の読み取り権限）を整理する。

## 1. 問題設定

Agent Skills の標準形式は、`SKILL.md` に書かれた手順を LLM が読み、その場の会話の中で実行することを前提にしている。この形式は配布と可搬性に優れるが、実行の単位としては次の限界がある。

1. **状態の置き場所が会話しかない。** 複数回の呼び出しにまたがる作業状態（調査済みの対象、蓄積した所見、検証の成否）は会話文脈に書くしかなく、文脈圧縮やセッション再開で失われうる。
2. **呼び出しに型がない。** Skill の一部の手順だけを、決まった入力で呼び、決まった形の結果を受け取る手段がない。呼び出しは毎回、自由文の指示として再構成される。
3. **並行する文脈で状態が混ざる。** 同じ Skill を別セッションや別ルームで使うとき、状態の分離は会話の分離に依存し、仕組みとしては保証されない。
4. **ツールの保持がプロセス共有である。** 現行のツール保持はプロセス全体で1つの辞書であり、ある使用者が保持したツールを別の使用者の終了処理が解除しうる。単一の Skill を順に使う範囲では問題にならないが、複数の実行主体が同時に存在すると破綻する。

本拡張は、これらの限界に対して「配布形式は標準のまま、実行時だけオブジェクトとして扱う」という方向で答える。

## 2. 先行例と位置づけ

- **Agent Skills 標準**（agentskills.io）は手順書型を前提とし、状態やメソッドの概念を持たない。本拡張はこの形式を置き換えず、その上に実行時の意味を重ねる。
- **Microsoft Agent Framework の ClassSkill** は、クラスベースの Skill をコードとして書く先例である。ただし配布単位がコードであり、Markdown 手順書の可搬性とは相容れない。本拡張は「クラスらしさ」を実行時の振る舞い（インスタンス、メソッド、状態）に限定し、配布形式には持ち込まない点で分かれる。
- **AgentFile 関連提案**（agentskills/agentskills#178、正式標準ではない）はファイル形式側の拡張を論じる。本拡張は形式の標準化を待たず、UAG 内のオプトイン拡張として閉じる道を選んだ。標準化の議論が進めば追随を検討するが、それを前提にしない。

## 3. 設計判断と、捨てた案

### 3.1 採用: `metadata` の関連付け + 独立ファイル

拡張定義は `SKILL.md` の `metadata` から別ファイル `uag-object.yaml` を指す形にした。当初候補の任意トップレベル項目（`x-uag` 等）を増やす案は、厳格な外部バリデータとの互換性を損なうため捨てた。マーカーのない Skill は新ランタイムに自動変換しない（オプトインの原則）。

### 3.2 採用: 定義とインスタンスの分離

Skill 定義（クラスに相当）と実行インスタンスを分け、状態はインスタンスが持つ。これにより、同一 Skill の同時利用でも状態が混ざらず、状態の寿命をセッションとインスタンスの組で定義できる。定義側のライフサイクル（審査・有効化）と実行側の状態（active / finished 等）を分けることも、この分離の帰結である。

### 3.3 採用: 定義スナップショットのハッシュ固定

インスタンス作成時に、参照される全ファイル（メソッド本文、スキーマ群とその参照先）のバイト列を固定し、ハッシュで照合する。実行中に定義が変わったら黙って新しい内容で続けず、明示的なエラーにする。利便性（編集したら即反映）より、再現性と監査可能性を優先した判断である。

### 3.4 採用: 状態更新の検証と楽観的排他制御

`prompt` 型メソッドの結果は `result` と `state_update` に分けて構造化出力で受け取り、スキーマで検証できた変更だけを、版番号の照合（CAS）を伴って適用する。LLM に保存状態を直接書かせない。検証に失敗した呼び出しは状態を変えない。

### 3.5 採用: ツール保持の所有者つきリース

プロセス共有の保持辞書は残し（既存の意味を変えない）、インスタンス向けに所有者つきリースを併設する。共有辞書のまま複数インスタンスに適用する案は、終了処理の競合で破綻するため捨てた。

### 3.6 採用: 継承・インターフェース・オーバーライド（制限付き）

当初は合成を先行させ、継承は実需を見てからとする案だったが、利用者（鵜川）の判断で初期仕様に含めることにした（2026-11-27）。ただし無制限にはしない。次の制限を付けた。

- **単一継承のみ。** 多重継承は、同名メソッドや同名状態キーの解決順序という、Skill の作者に読めない規則を持ち込むため採用しない。複数の契約が必要な場合は、複数実装できるインターフェースで受ける。
- **状態スキーマは追加のみ。** 親の状態キーの削除と型変更を禁止する。親のメソッドは親の状態の形を前提に書かれており、子が形を壊すと引き継いだメソッドが実行時に破綻するためである。初期値は子で上書きできる。
- **オーバーライドは入出力を親と同一にし、実装だけを差し替える。** 呼び出し側から見た契約が不変なので、合成やインターフェース経由の呼び出しが置き換えで壊れない。
- **インターフェース定義は Skill のフォルダ内に置く。** 共有の置き場所を新設せず、パスの安全規則と Skill 単位の配布をそのまま使う。
- **検証はすべて PR1（検証のみの段階）に入れる。** 継承とインターフェースの解決・照合を実行時の直前まで遅らせないことで、定義の誤りを読み込み時点で報告できる。
- **オーバーライドしたメソッドの振る舞いは作者の責任とする。** 継承しただけなら、親の性質（最後までやり遂げる、など）はそのまま残る。しかしオーバーライドした時点で、そのメソッドの振る舞いは子の作者の責任であり、親の性質は保証されない。「最後までやり遂げたか」は実行しないと判定できないため、検証で守るのは入出力の契約までとする。

### 3.7 原則: `allowed-tools` は権限ではない

`allowed-tools` はツールのロードと保持のための宣言であり、実行権限の付与とは解釈しない。実際の実行は既存のポリシー判定と確認の経路を通す。この原則は、Skill の有効化を権限付与と誤読する事故を防ぐために明記する。

## 4. 互換性契約を先に固定する理由

本拡張の成否は、新機能の便利さよりも「既存 Skill が無変更で従来どおり動くか」で決まる。そのため設計では、実装に先立って互換性の条件を10項目で固定し、満たさない変更を受け入れない規則にした。段階分割（検証のみ → 永続化 → 実行 → 合成）も同じ考え方で、各段階で互換性の回帰を確認してから次へ進む。

## 5. 未解決の論点

1. **メソッドの呼び出し口。** LLM が `create` / `call` をどういう道具立てで使うかは未定である。永続化（PR2）より前に形を決めないと、使い方と合わない保存設計になる恐れがある。
2. **既存のツール文脈保存との重なり。** UAG にはすでに、ツールごとの文脈を Session Store の `tool_context_states` テーブルに保存する仕組みが実装され、画像ツール等が使っている（`core_impl/responses_state.py` の `set_tool_context`）。キー付け（ツール単位か、インスタンス単位か）、スキーマ検証の有無、排他制御の有無が本拡張の状態管理と異なる。PR2 の前に両者を突き合わせ、状態保存を二重に作らないことを確認する必要がある。
3. **状態の読み取り権限。** インスタンス間の分離は設計されているが、ルームやユーザーをまたぐ読み取りの境界は、識別子に文脈を持たせるという段階に留まる。メモリ V3 で共有境界が問題になった経緯があり、ここでも同じ観点の詰めが要る。
4. **構造化出力への依存。** `prompt` 型メソッドの成否は、利用するプロバイダとモデルが `result` / `state_update` の形を安定して返せるかに依存する。対応能力の低いモデルでは失敗率が上がるため、失敗時の扱い（再試行するか、そのまま失敗として返すか）を運用前に決める必要がある。

## 6. 評価方法

- **互換性**: 設計書の受け入れテスト群（旧 Skill の読み込み・一覧・終了処理が無変更であること、不正な拡張定義が従来動作を壊さないこと）を全段階で回帰確認する。
- **継承と契約の検証**: 継承チェーンの循環、オーバーライドの入出力不一致、状態キーの削除・型変更、インターフェースのメソッド欠落は、すべて読み込み時点の検証で弾けることを受け入れテストで確認する。実行時に初めて発覚する形にはしない。
- **実例による検証**: 設計書の例（python-review）だけでなく、実在の Skill を1つこの形式で書き、メソッド呼び出しと状態の持ち回しが実際の作業で機能するかを確認する。実例で破綻する設計は、仕様の側を直す。
- **成功の定義**: 既存 Skill の回帰ゼロを保ったまま、状態を持つ Skill が文脈圧縮とセッション再開をまたいで作業を継続できること。

## 7. 結論

手順書型 Skill の可搬性は保ちたい。しかし実行の単位としては、状態と型付き呼び出しが要る場面がある。本拡張は、配布形式を標準のままにし、明示的に選んだ Skill だけを実行時オブジェクトとして扱うことで、この2つを両立させる試みである。継承・インターフェース・オーバーライドは、単一継承、状態の追加のみ、入出力不変のオーバーライドという制限のもとで初期仕様に含めた。残る論点は呼び出し口と既存の状態保存との関係に集中しており、段階分割の早い段階で決着させる。
