# uagent 改善設計書（実施順序版）

- 作成日: リポジトリ確認時
- 対象: `./`（uagent リポジトリ）
- 方針: 大規模な分割を先に行わず、**安全性・再現性・観測可能性を確保してから、内部構造を整理する**。
- 重要事項: すべての新規ユーザー向け文言は I18N 対応を前提とする。日本語だけで実装して後から翻訳する進め方は禁止する。

## 1. 現状認識

### 1.1 確認した構成

- 実行中核: `src/uagent/core.py`、`src/uagent/uagent_llm.py`
- インターフェース: `src/uagent/cli.py`、`src/uagent/scheckgui.py`、`src/uagent/web.py`
- ツール基盤: `src/uagent/tools/__init__.py`
- MCP: `src/uagent/tools/mcp/`
- A2A: `src/uagent/a2a/`
- ランタイム補助: `src/uagent/runtime/`
- 翻訳基盤: `src/uagent/i18n.py`、`src/uagent/locales/`
- テスト: `tests/` に MCP OAuth、ツール安全性、プラグイン、provider capability などのテストがある

### 1.2 主要な問題

1. **A2A キャンセルが実行停止を意味していない**

   - `src/uagent/a2a/server.py` の `cancel_task` は状態を `CANCELLED` に変更するだけ。
   - バックグラウンドの `asyncio.create_task()` は保持されず、`run_once()` が完了した際に結果を上書きする余地がある。
   - `src/uagent/a2a/task_store.py` は状態を保持するが、実行ハンドルや状態遷移を管理していない。

1. **実行時に pip install する経路がある**

   - `src/uagent/_pip_auto.py` が ImportError 時に pip を実行する。
   - 実行環境の再現性、権限、オフライン利用、ソフトウェア供給網の管理に影響する。

1. **`core.py` の責務が多い**

   - console/stdio、設定、履歴、ログ、プロンプト、応答状態、割り込みなどが集中している。
   - `llm_round_helpers.py` 等との依存が強く、循環依存と変更影響範囲の拡大につながる。

1. **ツール安全性が並列可否中心である**

   - 読み取り、外部送信、冪等更新、破壊的操作を同じ尺度で扱いにくい。

1. **MCP OAuth metadata discovery の境界が曖昧**

   - `src/uagent/tools/mcp/oauth_metadata.py` は Resource Server の URL を origin に切り詰めて Well-Known URL を作る。
   - パス配下のサーバー、issuer 検証、HTTP/HTTPS、リダイレクト時の信頼境界を resolver として一元管理しにくい。

1. **I18N を新しい境界・非同期処理へ引き継ぐ設計が不足している**

   - `src/uagent/i18n.py` は gettext、`UAGENT_LANG`、スレッド単位の言語設定を提供している。
   - ただし A2A のバックグラウンド task、Web の部屋単位、SSE、例外・ツール policy の新規メッセージでは、言語コンテキストを失わない設計が必要である。

## 2. 私の推奨する作業順序

### 全体順序

```text
0. ルール固定・計測
   ↓
1. A2A task lifecycle とキャンセル
   ↓
2. auto-install の安全化
   ↓
3. I18N 共通契約とエラー/ログ境界
   ↓
4. MCP OAuth resolver（既存認証の安全性）
   ↓
5. Tool Safety Policy
   ↓
6. Provider Capability Registry
   ↓
7. core.py の段階分割
   ↓
```

この順番を推奨する理由は、最初に外部 API の状態不整合と実行環境の予期しない変更を止め、その後に共通契約（I18N、エラー、policy）を決め、最後に大きな内部リファクタリングを行うためである。

## 3. フェーズ 0: 改修ルールと計測を固定する

### 目的

後続の変更で「動いたが安全性または翻訳を壊した」という状態を防ぐ。

### 作業内容

1. 既存テストを改修前の基準として実行する。
1. `pytest` の通常テスト、optional dependency テスト、統合テストを marker で区分する。
1. 新規ユーザー向け文言のルールを `AGENTS.md` または開発ガイドへ明記する。
1. import graph の検査を CI に追加し、`core` を新規モジュールから逆参照しないルールを設ける。
1. 構造化ログの最低項目を決める。

### I18N のルール（この時点で固定）

- ユーザーに見える文言は必ず `from .i18n import _` 経由にする。
- 例外メッセージ、CLI の `help`、Web/A2A の status/error、SSE の表示文言も対象とする。
- 翻訳キーは動的な完成文ではなく、安定した msgid とする。
- 変数は `%()` プレースホルダーまたは既存の gettext 互換形式を使い、翻訳文字列内に値を埋め込んでから渡さない。
- 内部ログは英語の固定 event code を持ち、表示用 message は必要な場合だけ翻訳する。
- ツールや外部サーバーから返った文言は原文として扱い、無断翻訳しない。UI 表示用のラベルだけを自アプリの I18N 対象にする。
- `en` を必ず fallback とし、翻訳欠落で処理を失敗させない。

### 完了条件

- 基準テスト結果を保存できる。
- I18N の lint/review 観点が決まっている。
- 追加するイベント ID、エラーコード、翻訳 msgid の命名規則が決まっている。

## 4. フェーズ 1: A2A タスクライフサイクルを直す（最優先）

### 目的

A2A の「キャンセル済み」と「実際の実行状態」を一致させる。

### 設計

`TaskRecord` の公開状態と、内部の実行ランタイムを分離する。

```python
class TaskStatus(str, Enum):
    IN_PROGRESS = "IN_PROGRESS"
    SUCCEEDED = "SUCCEEDED"
    FAILED = "FAILED"
    CANCEL_REQUESTED = "CANCEL_REQUESTED"
    CANCELLED = "CANCELLED"

@dataclass
class TaskRuntime:
    asyncio_task: asyncio.Task[None] | None
    cancel_event: asyncio.Event
    locale: str
```

`TaskRuntime` は API レスポンスへ出さず、`InMemoryTaskStore` 内で管理する。状態遷移は次に限定する。

```text
IN_PROGRESS -> SUCCEEDED
IN_PROGRESS -> FAILED
IN_PROGRESS -> CANCEL_REQUESTED -> CANCELLED
```

### 実装順

1. `TaskStatus` と atomic transition の unit test を先に追加する。
1. `message_send` の `asyncio.create_task()` 戻り値を store に登録する。
1. `cancel_task` で `CANCEL_REQUESTED`、cancel event、task cancel を順に扱う。
1. `_execute_task` で `CancelledError` と通常例外を回収する。
1. 終端状態の compare-and-set を行い、キャンセル後の成功・失敗で上書きしない。
1. `subscribe_task` と `message_stream` の SSE イベントを状態遷移に合わせる。
1. タスク作成時に locale を保存し、バックグラウンド実行時にも同じ locale を復元する。

### I18N の具体化

- A2A API の機械的な `code` は固定値（例: `TASK_NOT_FOUND`）とし、`message` は `_()` で生成する。
- API が機械処理を前提とする場合、`message` の言語は request の `Accept-Language`、`UAGENT_LANG`、サーバー既定値の順で決定する。
- `TaskRecord` の `status` は翻訳しない固定 enum。画面表示時に `task.status.in_progress` 等の msgid へ変換する。
- SSE の `type`、`status`、`code` は翻訳しない。表示用 `label` や `message` のみ翻訳する。
- locale が不正または未対応の場合は `i18n.py` の既存 fallback に委譲する。

### テスト

- 即時返却タスクの完了・失敗・キャンセル。
- 二重キャンセル、完了済みキャンセル、同時 cancel。
- キャンセル後に `SUCCEEDED`/`FAILED` へ戻らないこと。
- `ja`/`en` の A2A error と SSE 表示。
- background task が locale を失わないこと。

## 5. フェーズ 2: auto-install を安全化する

### 方針

`src/uagent/_pip_auto.py` の API と、既存の自動インストール体験は維持する。既定動作は自動インストールありとし、環境を変更したくない利用者が明示的に無効化できる設計にする。

```text
UAGENT_AUTO_INSTALL=allow     # 既定。ImportError 時に自動導入を試行
UAGENT_AUTO_INSTALL=prompt    # TTY の対話時だけ確認して導入
UAGENT_AUTO_INSTALL=off       # 明示的に自動導入を無効化
```

`prompt` は TTY の対話時だけ確認し、A2A、Web サーバー、CI、非 TTY では確認なしに導入しない。既定の `allow` では、既存実装と同様に ImportError 時の自動導入を試行する。導入対象はアプリケーションが定義した optional dependency に限定し、無制限のパッケージ名を受け付けない。

### 作業内容

- `install_with_status()` に policy 判定を追加する。
- pip を実行しない場合は、必要な package と `pyproject.toml` の extra 名を含む案内を返す。
- import fallback は元の ImportError を隠さず、導入方法を付加する。
- `docs/README_AUTO.md`、環境変数ドキュメント、Quickstart を更新する。
- 新規エラー文言は `_()` で翻訳する。package 名、extra 名、コマンド部分は保護する。

### 完了条件

- `off` で pip subprocess が一度も呼ばれない。
- optional dependency 不足時も、英語・日本語の導入案内が表示される。
- CI がネットワークなしでも再現可能に動く。

## 6. フェーズ 3: I18N とエラー境界を共通化する

フェーズ 1、2で必要になったため、ここで I18N を独立した設計として固める。大規模な `core.py` 分割より先に実施する。

### 6.1 メッセージの分類

| 種類 | 例 | 言語化 |
|---|---|---|
| protocol field | `TASK_NOT_FOUND`、`IN_PROGRESS` | しない |
| event code | `a2a.task.cancel_requested` | しない |
| user message | `Task was cancelled.` | `_()` で言語化 |
| tool raw output | 外部ツールの返答 | 原文を保持 |
| UI label | `Cancel task` | `_()` で言語化 |
| diagnostic detail | package名、URL、status code | 値は保護し、周辺文言のみ言語化 |

### 6.2 I18N コンテキスト

`i18n.py` の thread-local 設計は同期処理には有効だが、async task をまたぐ場合の引き継ぎを明示する。

```python
@dataclass(frozen=True)
class LocaleContext:
    language: str

async def with_locale(ctx: LocaleContext, coro: Awaitable[T]) -> T:
    token = set_contextvar_locale(ctx.language)
    try:
        return await coro
    finally:
        reset_contextvar_locale(token)
```

実装方針:

- 新規の非同期境界では `contextvars.ContextVar` を第一候補にする。
- 既存の `set_thread_lang()` は互換 API として残す。
- Web の room/request locale、A2A の request locale、CLI の process locale をそれぞれ明確にする。
- locale は request/task に保存し、グローバル変数で切り替えない。
- ログは `event_code` と locale を別フィールドにし、翻訳後の全文だけを検索キーにしない。

### 6.3 翻訳カタログ運用

- 新規 msgid は英語を原文として追加する。
- 日本語訳を同時に追加し、未翻訳は英語 fallback にする。
- msgid の変更は翻訳を壊すため、可変値を msgid に含めない。
- `src/uagent/locales/*/LC_MESSAGES/uag.po` と `.mo` の生成手順を CI で検証する。
- CLI、GUI、Web、A2A、MCP、ツール policy の代表的な画面文言を各言語で smoke test する。
- Markdown の説明文や README の翻訳はコード内 msgid とは別管理にする。

## 7. フェーズ 4: MCP OAuth resolver を整理する

### 作業内容

`src/uagent/tools/mcp/oauth_metadata.py` に候補 URL を返す resolver を追加する。

1. scheme、authority、path を分解する。
1. RFC 9728/8414 に基づき、パスあり・origin・既知 URL の候補を順序付けする。
1. 候補を取得し、HTTP status と JSON schema を検証する。
1. `resource` と期待 URL、`issuer` と期待 issuer を正規化比較する。
1. HTTPS を既定とし、HTTP は localhost または明示的な開発設定だけ許可する。
1. リダイレクト先・authorization endpoint の trust boundary を検証する。
1. 既存の単一 URL 関数は互換 shim として残す。

### I18N とセキュリティメッセージ

OAuth のエラー code は固定値にする。ユーザー向け説明は `_()` を通し、URL、issuer、status code は placeholder として挿入する。token、client secret、authorization code はエラーメッセージ・翻訳・ログへ出さない。

### テスト

- origin、パス、末尾 slash、URL encoding。
- issuer/resource mismatch。
- redirect、HTTP/HTTPS、候補 fallback。
- 既存 MCP OAuth unit/integration/security test の回帰。

## 8. フェーズ 5: Tool Safety Policy を導入する

既存の `is_parallel_safe` / `run_tools_parallel` を壊さず、上位概念を追加する。

```python
class SideEffect(str, Enum):
    READ_ONLY = "read_only"
    IDEMPOTENT_WRITE = "idempotent_write"
    EXTERNAL_SEND = "external_send"
    DESTRUCTIVE = "destructive"

@dataclass(frozen=True)
class ToolPolicy:
    side_effect: SideEffect
    parallel_safe: bool = False
    resource_key: str | None = None
    requires_confirmation: bool = False
```

### ルール

- `READ_ONLY` だけを既定で並列化する。
- 同一 `resource_key` は直列化する。
- `EXTERNAL_SEND` と `DESTRUCTIVE` は確認を必須にする。
- 旧 `x_parallel_safe` は移行期間だけ fallback として利用する。
- 未分類は直列・確認要求側に倒す。
- policy の判定結果をログへ残す。

### I18N

確認画面、拒否メッセージ、タイムアウト、policy の説明は `_()` 対象とする。`side_effect` の enum 値や tool 名は固定値として翻訳しない。ツール提供者が定義する description は原文と翻訳済み UI ラベルを分離する。

## 9. フェーズ 6: Provider Capability Registry

`src/uagent/providers/provider_caps.py` を静的な provider metadata と runtime 検出の窓口にする。`llmcapa_util.py` の既存判定ロジックを一度に捨てず、registry の内部実装として移行する。

```python
@dataclass(frozen=True)
class ProviderSpec:
    name: str
    capabilities: frozenset[str]
    supports_tools: bool
    supports_streaming: bool
    supports_vision: bool

class ProviderRegistry(Protocol):
    def resolve(self, provider: str, model: str | None = None) -> ProviderSpec: ...
```

- unknown capability は「非対応」と同じではなく `unknown` とする。
- ツール送信のような安全に関わる判定は unknown を拒否側に倒す。
- provider 名、capability 名、エラー code は翻訳しない。
- UI の説明、非対応理由、設定案内は `_()` で言語化する。

## 10. フェーズ 7: `core.py` を段階的に分割する

ここまでに状態、エラー、I18N、policy の契約が定まっているため、この段階で分割する。先に分割すると、問題の境界まで一緒に移動してしまうため避ける。

### 分割先

```text
src/uagent/runtime/
  session.py          # AgentSession、1 ラウンドのライフサイクル
  state.py            # 状態、イベント、応答 model
  console.py          # VT/stdio/encoding
  history.py          # 履歴
  logging_setup.py    # ログ、mask、correlation ID
  prompt_context.py   # prompt の組み立て
  cancellation.py     # interrupt/cancel token
```

### 移行順

1. 関数を新モジュールへ移し、`core.py` から re-export する。
1. 新機能は新モジュールへだけ追加する。
1. CLI/Web/A2A が `AgentSession` を利用する。
1. `llm_round_helpers.py` の `core` 参照を state/port 参照へ変える。
1. `uagent_llm.py` は provider adapter と session port だけに依存させる。
1. 循環 import を CI で検査する。

### I18N

- `console.py` は翻訳を担当せず、表示層へ msgid/message を渡す。
- `session.py` は固定 event code と locale context を返す。
- prompt のシステム文言は UI 文言とは別の翻訳資産として管理する。
- 履歴には locale を必要に応じて保存し、再表示時の言語切替要件を明確にする。

## 11. フェーズ 8: OAuth 共通層と運用改善

MCP 固有の `oauth_*.py` から、次の汎用部品を `src/uagent/auth/` へ抽出する。

- PKCE、state、nonce、redirect 検証
- token store の暗号化・ロック
- metadata 取得と issuer/resource 検証
- OAuth error の正規化

MCP は adapter として利用し、A2A や将来の connector から再利用する。旧 import path は互換 shim で維持する。

運用面では、task ID、相関 ID、provider、tool、policy、locale、event code を構造化ログに記録する。ただし token、secret、authorization code、個人情報は mask または記録禁止とする。

## 14. 実施ログと設計書への追記

- 改修前の `pytest tests` を実行し、既存の 10 件の失敗を基準結果として確認した。失敗はスクリーンショット環境依存、ANSI 表示環境依存、既存 I18N カタログ不足、既存ツール実装の I18N lint 違反であり、今回の A2A/auto-install 改修とは独立している。
