# Стиснення контексту та обмежений контекст моделі

uag використовує кілька рівнів для забезпечення обмеженості активного контексту моделі. Мета полягає в скороченні зайвих вхідних токенів без видалення файлів, результатів роботи інструментів або даних сеансу, які можуть ще знадобитися користувачеві.

Цей документ описує поточну реалізацію. У ньому також проводиться розмежування між детермінованою поведінкою та поведінкою, що залежить від конкретного постачальника або підтримується LLM.

## 1. Динамічний набір інструментів

Не кожне визначення інструменту потрібно надсилати до моделі на кожному кроці.

- `tool_catalog` здійснює пошук серед доступних можливостей.
- `tool_load` увімкне лише ті інструменти, які необхідні для поточного завдання.
- `tool_catalog`, `tool_load` та `unload_tool` залишаються доступними як засоби управління.
- Потоки Responses API, сумісні з GPT-5.4, можуть використовувати вбудований серверний Tool Search.
- Застарілий режим Tool Search звужує специфікації інструментів за допомогою `tool_catalog` на стороні клієнта.

Це зменшує кількість вхідних токенів, що використовуються схемами інструментів, особливо в установках із великою кількістю інструментів.

## 2. Великі текстові результати інструментів стають артефактами

Коли текстовий результат інструменту перевищує поріг Artifact, uag зберігає повний результат як Artifact і надсилає моделі обмежене посилання та попередній перегляд замість повного тексту.

Стандартні обмеження такі:

```text
UAGENT_TOOL_RESULT_ARTIFACT_THRESHOLD_CHARS=100000
UAGENT_TOOL_RESULT_MAX_CHARS=12000
```

Представлення, доступне для моделі, містить назву інструменту, початкову довжину, посилання `artifact://`, шлях до сховища та обмежений попередній перегляд. Повний результат залишається доступним через сховище Artifact.

Поріг можна змінити за допомогою `UAGENT_TOOL_RESULT_ARTIFACT_THRESHOLD_CHARS`. Значення `0` вимикає просування Artifact. `UAGENT_TOOL_RESULT_MAX_CHARS` керує звичайною політикою обмежених результатів; `0` вимикає це звичайне обмеження.

## 3. Обмежений витяг даних з Artifact

Інфраструктурний інструмент `artifact_read` витягує лише запитувану частину Artifact:

- `start_line` вибирає перший рядок.
- `max_lines` обмежено до 500.
- `max_chars` обмежено до 50 000 символів.
- Можна використовувати як ідентифікатор Artifact, так і URI `artifact://`.

Це дає змогу перевіряти невеликий релевантний діапазон замість повторного введення всього файлу або результату команди в наступний цикл роботи моделі.

Нові артефакти зберігаються нижче:

```text
~/.uag/artifacts/
```

Існуючі старі шляхи Artifact залишаються доступними для читання з метою сумісності.

## 4. Ізоляція бінарного навантаження

Вбудовані бінарні дані не надсилаються як текстовий результат інструменту до наступного циклу моделі. Поля у форматі Base64 замінюються коротким маркером, наприклад:

```text
[бінарні дані опущені з контексту LLM]
```

Інтерфейс користувача та віддалені клієнти все ще можуть отримувати вкладення в пам’яті, а збережені файли залишаються доступними через їхні шляхи або посилання Artifact. Це запобігає збільшенню розміру текстового контексту моделі за рахунок зображень, аудіо, знімків екрана та інших бінарних даних.

Бінарні дані одного й того ж класу очищаються перед збереженням у SQLite та JSONL, що запобігає їхньому поверненню у вигляді великих даних після перезавантаження сесії.

## 5. Автоматичне стиснення історії

uag може стискати старі записи історії розмов, коли кількість повідомлень або оціночна кількість токенів досягає заданого ліміту.

Політика стиснення використовує:

- кількість несистемних повідомлень;
- вирішене контекстне вікно моделі, якщо воно доступне;
- `UAGENT_SHRINK_KEEP_LAST` (за замовчуванням — 20);
- `UAGENT_SHRINK_MAX_TOKENS` або перезапис, специфічний для моделі;
- `UAGENT_SHRINK_CNT`; та
- `UAGENT_SHRINK_RATIO` (за замовчуванням — 0,5, якщо вікно контексту відоме).

Обмеження, специфічне для моделі, можна вказати у вигляді:

```text
UAGENT_SHRINK_MAX_TOKENS_<MODEL_NAME>
```

Попереднє узагальнення не генерується заново на кожному кроці. Для повторного запуску стиснення необхідне накопичення достатнього обсягу нової історії або черговий переповнення бюджету токенів.

## 6. Підсумки історії з використанням LLM

Коли автоматичне стиснення використовує LLM, старі повідомлення користувачів, помічників та інструментів узагальнюються у поточне системне повідомлення, тоді як найсвіжіша частина зберігається.

Довгі історії можна узагальнювати частинами. Відповідні параметри:

```text
UAGENT_SHRINK_CHUNK_SIZE=100
UAGENT_SHRINK_SINGLE_SHOT=1
```

Підсумок згортається вперед, а не створює необмежену послідовність підсумкових повідомлень. Це операція, що підтримується LLM, і може вимагати додаткових запитів до провайдера.

## 7. Детерміноване резервне стиснення

Якщо підсумок LLM недоступний, uag може зберегти початкові системні повідомлення та лише найсвіжіші повідомлення. Межі викликів інструментів відновлюються таким чином, щоб отриманий журнал не починався і не закінчувався «покинутим» викликом інструменту.

Завантажувач та санітайзер також видаляють записи, що не стосуються моделі або є недійсними, зокрема повідомлення, призначені лише для інтерфейсу користувача, внутрішні контрольні повідомлення, пошкоджені рядки журналу, непідтримувані ролі, «покинуті» результати інструментів та неповні блоки викликів інструментів.

Під час перезавантаження сеансу відновлюється поточний системний запит, а зберігаються лише відповідні вставлені системні повідомлення, такі як контекст навичок або хуків.

## 8. Відновлення після переповнення контексту

Якщо провайдер повідомляє про перевищення вікна контексту, uag визначає велике повідомлення з недавньої історії та скасовує це повідомлення та наступну історію перед повторною спробою. Це реактивний резервний варіант, а не заміна звичайного обмеження розміру.

## 9. Продовження та ущільнення на стороні провайдера

У разі підтримки функції Responses API використовує `previous_response_id` для продовження ланцюжка відповідей без повторної відправки з клієнта всієї історії відповідей, якою керує провайдер.

Потоки Responses API також надсилають конфігурацію ущільнення на стороні провайдера, використовуючи той самий локальний поріг стиснення. Точна поведінка залежить від провайдера; локальні Artifact та політики історії залишаються незалежними від провайдера запобіжними заходами.

## 10. Ефективність підрахунку токенів

Кількість токенів, що використовується для прийняття рішень щодо стиснення, кешується та оновлюється інкрементально, коли додаються лише нові повідомлення. Це безпосередньо не зменшує контекст моделі, але знижує навантаження на процесор та затримку при прийнятті рішення про необхідність стиснення.

## Що ще не є повністю уніфікованим рівнем

Поточна реалізація ще не забезпечує всіх наведених нижче елементів у вигляді єдиного менеджера, незалежного від провайдера:

- уніфіковані `ContextManager` та `ContextBudget`;
- `ToolResultRecord` з метаданими про важливість та витіснення;
- семантичні резюме, які не потребують `LLM`;
- автоматичне вилучення та повторне введення відповідних артефактів;
- центральний менеджер результатів, що гарантує перетворення `Artifact` для кожного інструменту, який генерує бінарні файли; або
- витіснення з урахуванням пріоритету у всіх категоріях: системній, історії, схеми інструменту та результатів.

Коротко кажучи, uag наразі поєднує детерміноване урізання, посилання на Artifact, ізоляцію бінарних файлів, динамічний вибір інструментів, резюме історії, продовження роботи постачальника та відновлення після переповнення. План розробки уніфікованого контекстного шару викладено в [UAG_CONTEXT_MANAGEMENT_DESIGN.md](UAG_CONTEXT_MANAGEMENT_DESIGN.md).
