# 上下文压缩与有界模型上下文

uag 通过多层机制来确保活动模型上下文处于有界状态。 其目标是减少不必要的输入令牌，同时不删除用户可能仍需要的文件、工具结果或会话数据。

本文档描述了当前的实现。它还区分了确定性行为与提供商特定行为或由 LLM 辅助的行为。

## 1. 动态工具界面

并非每个回合都需要将所有工具定义发送至模型。

- `tool_catalog` 搜索可用功能。
- `tool_load` 仅启用当前任务所需的工具。
- `tool_catalog`、`tool_load` 和 `unload_tool` 仍作为管理工具可用。
- 兼容 GPT-5.4 的 Responses API 流程可使用原生服务器端的 Tool Search。
- 旧版 Tool Search 模式通过客户端的 `tool_catalog` 缩小工具规范范围。

这可减少工具模式所使用的输入令牌数量，特别是在安装了大量工具的环境中。

## 2. 大型文本工具结果将转换为工件

当文本工具结果超过 Artifact 阈值时，uag 会将完整结果作为 Artifact 存储，并向模型发送一个受限引用和预览，而非全文。

默认限制如下：

```text
UAGENT_TOOL_RESULT_ARTIFACT_THRESHOLD_CHARS=100000
UAGENT_TOOL_RESULT_MAX_CHARS=12000
```

模型可见的表示形式包含工具名称、原始长度、一个 `artifact://` 引用、存储路径以及受限预览。 完整结果仍可通过 Artifact 存储库获取。

阈值可通过 `UAGENT_TOOL_RESULT_ARTIFACT_THRESHOLD_CHARS` 进行调整。值为 `0` 时将禁用 Artifact 提升功能。`UAGENT_TOOL_RESULT_MAX_CHARS` 控制常规的有界结果策略；`0` 时将禁用该常规限制。

## 3. 有限范围的 `Artifact` 检索

`artifact_read` 基础架构工具仅检索 `Artifact` 中请求的部分：

- `start_line` 选择第一行。
- `max_lines` 上限定为 500。
- `max_chars` 上限定为 50,000 个字符。
- 既可以使用 Artifact ID，也可以使用 `artifact://` URI。

这使得可以检查一小段相关内容，而无需将整个文件或命令结果重新注入到下一个模型迭代中。

新生成数据存储如下：

```text
~/.uag/artifacts/
```

出于兼容性考虑，现有的旧版 Artifact 路径仍可读取。

## 4. 二进制有效载荷隔离

内联二进制数据不会作为文本形式的工具结果发送至下一个模型迭代。 Base64 格式的字段将被替换为简短标记，例如：

```text
[从 LLM 上下文中省略的二进制有效载荷]
```

UI 和远程客户端仍可接收内存中的附件，已保存的文件也可通过其路径或 Artifact 引用访问。 这可防止图片、音频、截图及其他二进制有效载荷导致文本模型上下文膨胀。

同一类别的二进制有效载荷在进行 SQLite 和 JSONL 持久化之前会经过净化处理，从而防止其在会话重新加载后以大型有效载荷的形式返回。

## 5. 自动历史记录压缩

当消息数量或预估令牌数量达到配置的阈值时，uag 可对较早的对话历史记录进行压缩。

压缩策略基于以下因素：

- 非系统消息的数量；
- 模型已解析的上下文窗口（如有）；
- `UAGENT_SHRINK_KEEP_LAST`（默认值为 20）；
- `UAGENT_SHRINK_MAX_TOKENS` 或模型特定的覆盖值；
- `UAGENT_SHRINK_CNT`；以及
- `UAGENT_SHRINK_RATIO`（当已知上下文窗口时，默认值为 0.5）。

模型特有的限制可通过以下方式指定：

```text
UAGENT_SHRINK_MAX_TOKENS_<MODEL_NAME>
```

并非在每个回合都会重新生成之前的摘要。 要再次进行压缩，需要积累足够的新历史数据，或者发生另一次令牌预算溢出。

## 6. LLM 辅助的历史摘要

当自动压缩使用 LLM 时，较旧的用户、助手和工具消息会被汇总到一个滚动系统消息中，同时保留最近的尾部内容。

长历史记录可以分块汇总。 相关控制参数如下：

```text
UAGENT_SHRINK_CHUNK_SIZE=100
UAGENT_SHRINK_SINGLE_SHOT=1
```

摘要会向前折叠，而非生成无限长的摘要消息序列。 这是一项由 LLM 辅助的操作，可能需要额外的提供商请求。

## 7. 确定性回退压缩

如果无法获得 LLM 摘要，uag 可以保留开头的系统消息以及仅保留最新的消息。 工具调用边界会被修复，以确保生成的历史记录不会以孤立的工具调用开头或结尾。

加载器和清理器还会移除与模型无关或无效的条目，包括仅限 UI 的消息、内部控制消息、损坏的日志行、不受支持的角色、孤立的工具结果以及不完整的工具调用块。

当会话被重新加载时，当前系统提示符将被恢复，且仅保留相关的注入系统消息（如技能或钩子上下文）。

## 8. 上下文溢出恢复

如果提供程序报告上下文窗口已超出，uag 会识别一条较大的近期历史记录消息，并在重试前回滚该消息及其后的历史记录。这是一种反应式回退机制，并非对常规资源分配机制的替代。

## 9. 提供商端的响应延续与压缩

在受支持的情况下，Responses API 会使用 `previous_response_id` 来延续响应链，而无需从客户端重新发送整个由提供商管理的响应历史记录。

Responses API 流还会使用相同的本地压缩阈值发送提供商端的压缩配置。具体行为取决于提供商；本地 Artifact 和历史记录策略仍作为提供商中立的保护措施。

## 10. 令牌计数效率

用于压缩决策的令牌计数会被缓存，并仅在新增消息时增量更新。 这虽然不会直接缩减模型上下文，但可降低判断何时需要压缩所产生的 CPU 开销和延迟。

## 尚未完全统一的层

当前的实现尚未将以下所有功能整合为一个提供商中立的管理器：

- 统一的 `ContextManager` 和 `ContextBudget`；
- 包含重要性和淘汰元数据的 `ToolResultRecord`；
- 无需依赖 `LLM` 的语义摘要；
- 相关工件的自动检索和重新注入；
- 一个中央结果管理器，确保对每个生成二进制文件的工具都进行 `Artifact` 转换；或
- 跨越所有系统、历史、工具模式和结果类别的优先级感知驱逐机制。

简而言之，uag 目前结合了确定性截断、Artifact 引用、二进制隔离、动态工具选择、历史摘要、提供者延续以及溢出恢复。 统一上下文层的设计路线图详见 [UAG_CONTEXT_MANAGEMENT_DESIGN.md](UAG_CONTEXT_MANAGEMENT_DESIGN.md)。
