# MCP 2026-07-28仕様対応

- Status: planned
- Priority: P1
- Source: [MCP 2026-07-28 Specification release](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Related implementation: `src/uagent/tools/handle_mcp_v2_tool.py`, `src/uagent/tools/mcp_tools_list_tool.py`, `src/uagent/tools/mcp_servers_shared.py`

## 目的

MCP 2026-07-28仕様の変更を調査・実装し、既存のStreamable HTTP対応と後方互換性を維持したまま、ステートレス通信、ヘッダーによるルーティング、キャッシュ、MRTR、認証強化へ段階的に対応する。

## 仕様変更の要点

- `initialize` / `initialized` と `Mcp-Session-Id` に依存しないステートレスなリクエスト
- `MCP-Protocol-Version`、`Mcp-Method`、`Mcp-Name` によるリクエスト識別
- 任意の `server/discover` による能力取得
- `resultType: "input_required"` と `inputResponses` によるMRTR
- `tools/list` 等の `ttlMs` / `cacheScope` と決定的な一覧順
- Tasksの `io.modelcontextprotocol/tasks` 拡張への移行
- RFC 9207のissuer（`iss`）検証、CIMDへの移行、issuer-bound credentials
- Roots / Sampling / Loggingおよび旧HTTP+SSE transportの非推奨化

## 実装フェーズ

### Phase 0: 現行実装の適合性調査

- [ ] 現在のMCPクライアントが`initialize`とセッションIDをどこで使用するか確認
- [ ] Streamable HTTP、SSE、stdioの経路を分離して整理
- [ ] 汎用の既存MCPサーバーとの互換性を確認
- [ ] MCP仕様バージョンを固定値にせず、サーバー・クライアント能力として扱う
- [ ] 既存接続を壊さない互換モードの要否を決定

### Phase 1: Stateless HTTP基盤

- [ ] `MCP-Protocol-Version` をリクエストへ付与
- [ ] `Mcp-Method` と`Mcp-Name`をJSON-RPC内容と整合する形で付与
- [ ] `Mcp-Session-Id` がなくても処理できる送受信経路を追加
- [ ] `initialize`必須の旧サーバーには旧方式でフォールバック
- [ ] サーバーごとのtransport / protocol capabilityを保持
- [ ] 認証headersとプロトコルheadersを分離して監査する

### Phase 2: Discoveryとキャッシュ

- [ ] `server/discover`対応を検討
- [ ] `tools/list`、`prompts/list`、`resources/list`、`resources/read`のcache hintsを解析
- [ ] `ttlMs`と`cacheScope`を尊重したローカルキャッシュを追加
- [ ] キャッシュキーにserver identity、URL、headers由来の秘密情報を含めない
- [ ] 決定的な一覧順を維持し、LLMへ渡すツール仕様の不要な変動を抑える
- [ ] キャッシュ無効化・期限切れ・サーバー変更時の再取得をテスト

### Phase 3: MRTR

- [ ] `resultType: "input_required"` を検出
- [ ] サーバー要求をユーザー確認・既存human_ask経路へ接続
- [ ] `inputResponses`を付けて元のリクエストを再送
- [ ] 確認拒否、タイムアウト、再送回数上限を定義
- [ ] 入力要求を外部コンテンツとして扱い、プロンプトインジェクション対策を適用

### Phase 4: Tasks拡張

- [ ] `io.modelcontextprotocol/tasks`の能力検出
- [ ] `tasks/get`ポーリングを必要なMCPサーバーだけに提供
- [ ] `tasks/update`通知の扱いを定義
- [ ] A2Aタスク状態と混同しない内部モデルを用意
- [ ] タイムアウト、キャンセル、再接続時の再開方針を決定

### Phase 5: 認証・廃止機能

- [ ] RFC 9207の`iss`検証
- [ ] authorization serverごとのissuer-bound credential確認
- [ ] CIMD対応の必要性を認証方式ごとに確認
- [ ] DCRは後方互換用として明示的に扱う
- [ ] 旧HTTP+SSE、Roots、Sampling、Loggingの利用箇所を洗い出す
- [ ] 少なくとも12か月の非推奨期間を考慮した警告・互換方針を決める

## 後方互換性

- 既存のStreamable HTTPサーバーとstdioサーバーを壊さない。
- 仕様バージョンを一律に強制せず、サーバーの能力と応答を確認する。
- セッションを必要とする旧サーバーには、明示的なlegacy transportとして接続する。
- 新仕様のstateless処理と、uag内部の会話状態・MCPツールキャッシュを混同しない。
- MCPのステートレス化はA2Aのタスク状態管理を変更するものではない。

## セキュリティ・運用上の注意

- `Mcp-Method` / `Mcp-Name`だけを信頼して認可せず、JSON-RPC本文と一致することを検証する。
- 認証headers、Cookie、Access Tokenをログやキャッシュキーへ保存しない。
- MRTRの入力要求やサーバー応答は外部コンテンツとして扱う。
- `server/discover`や一覧キャッシュにより、古いツール定義を長期間使用しない。
- 旧仕様へのフォールバックを無期限に隠れた動作として残さず、警告と廃止計画を持つ。

- [ ] MCPメソッド・ツール名ヘッダーが本文と一致する

- [ ] 認証情報や外部コンテンツがログ・キャッシュへ漏れない
- [ ] 既存の汎用Streamable HTTP MCP接続とstdio MCP接続の回帰テストが通る

## I18N境界

`src/uagent/mcp/` は内部protocol層とし、I18Nを持たせない。内部層はユーザー向け文章を生成せず、構造化エラーコード、protocol identifier、検出結果、詳細パラメータを返す。

```text
src/uagent/mcp/
  → I18Nなし、構造化エラーのみ

src/uagent/tools/mcp_tools_list_tool.py
src/uagent/tools/handle_mcp_v2_tool.py
  → I18Nあり、ユーザー・LLM向けメッセージへ変換
```

内部エラーの例:

```json
{
  "code": "MCP_PROTOCOL_VERSION_UNSUPPORTED",
  "operation": "connect",
  "details": {
    "requested": "2026-07-28",
    "server_version": "unknown"
  }
}
```

翻訳しない値:

- `MCP-Protocol-Version`
- `Mcp-Method`
- `Mcp-Name`
- `server/discover`
- `tools/list` / `tools/call`
- `input_required` / `inputResponses`
- `tasks/get` / `tasks/update`
- `MCP_PROTOCOL_VERSION_UNSUPPORTED`などのエラーコード

公開ツール層では、内部エラーコードをI18Nキーへ変換する。内部層で英語文面を判定・比較したり、翻訳済みメッセージを例外へ格納したりしない。

## I18N方針

MCPのprotocol identifierとユーザー向け説明を分離する。プロトコル値は翻訳せず、UIメッセージだけを翻訳対象にする。

### 翻訳対象

- protocol modeの表示名
- capability / discoveryの説明
- cache、MRTR、Tasksの状態表示
- 認証エラー・issuer mismatch・再接続・timeoutのメッセージ
- deprecated機能・legacy fallbackの警告
- ユーザー確認要求と拒否メッセージ

### 翻訳しない値

- `MCP-Protocol-Version`
- `Mcp-Method`
- `Mcp-Name`
- `server/discover`
- `input_required`
- `inputResponses`
- `tasks/get`
- `tasks/update`
- `ttlMs`
- `cacheScope`
- `CIMD`、`DCR`、`MRTR`、`RFC 9207`

### 実装ルール

- MCPツールのJSON定義へI18Nキーを追加する。
- 既存の38ロケールのキー集合を一致させる。
- placeholder、技術用語、protocol identifierを保護する。
- 翻訳不足、空文字、placeholder不一致をCIで検出する。
- 英語・日本語で実際のMCPエラー、MRTR確認、legacy警告を確認する。
- 翻訳処理でMCPリクエスト本文や認証情報を送信しない。

## 依存関係・リスク

- MCP仕様、SEP、SDKの実装差異があるため、仕様バージョンと実機サーバーを分けて検証する。
- 既存のMCPライブラリが2026-07-28仕様に未対応の場合、adapter層の追加が必要になる。
- stateless化とキャッシュ導入により、サーバー側状態を暗黙に期待している既存ツールが影響を受ける可能性がある。
- MRTRはユーザー確認とLLMのツール実行ループを跨ぐため、無限再送を防ぐ上限が必須である。
